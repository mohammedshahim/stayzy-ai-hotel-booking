## What was built

**Feature 22 — Stripe Webhook (backend-only, no UI):**
- `backend/src/routes/webhooks.routes.ts` — `POST /webhooks/stripe`, uses `express.raw({ type: "application/json" })`. Mounted directly in `app.ts` before `express.json()` (same raw-body-first pattern already used for better-auth), not through `routes/index.ts`.
- `backend/src/controllers/webhooks.controller.ts` / `backend/src/services/webhook.service.ts` — `constructStripeEvent` verifies the `stripe-signature` header via `stripe.webhooks.constructEvent`; `handleStripeEvent` dispatches `payment_intent.succeeded` → booking `confirmed`, `payment_intent.payment_failed` → booking `failed`, any other event type is a silent 200 no-op.
- `backend/src/middlewares/requireCronSecret.ts` — new middleware, checks `x-cron-secret` header against `env.CRON_SECRET` using `crypto.timingSafeEqual`.
- `POST /bookings/expire-stale` (`bookings.routes.ts`, behind `requireCronSecret`) — `bookings.controller.ts`'s `expireStale` → `booking.service.ts`'s `expireStaleBookings` → `booking.queries.ts`'s `expireStalePendingBookings(cutoffMinutes)`. Returns `{ count, bookingIds }`.
- `booking.queries.ts` additions: `findBookingByStripePaymentIntentId`, `confirmBookingIfPending`/`failBookingIfPending` (share a private `transitionBookingIfPending` conditioned on `WHERE status = 'pending_payment'`), `expireStalePendingBookings` (single conditional `UPDATE ... WHERE status = 'pending_payment' AND created_at < cutoff`).
- New env vars: `CRON_SECRET` (real random value already set in `backend/.env`), `BOOKING_EXPIRY_MINUTES` (default 20). Both added to `.env.example` too.

## Decisions made

- Cleanup sweep is a plain HTTP endpoint the developer (or any external scheduler later) calls — not an in-process `setInterval`/cron dependency. No cron/job-runner package exists in the project and no deployment pipeline exists yet (Phase 9 hasn't started). Doubles as a manual-trigger tool for local testing.
- Endpoint protection is a shared-secret header (`CRON_SECRET`), not `requireAdmin` — both existing auth middlewares (`requireAuth`, `requireAdmin`) are browser-session-based via better-auth cookies, which doesn't work for a machine caller with no browser session. A shared secret works identically for manual `curl` testing now and a real scheduler later, no rework needed.
- 20-minute expiry window (MVP-appropriate per developer, configurable via `BOOKING_EXPIRY_MINUTES`). Accepted tradeoff: a slow-settling payment method (e.g. ACH-style "Pay by bank", which Stripe can leave `processing` for hours) could have its late `succeeded` webhook arrive after the sweep already cancelled that booking. Both the webhook handler and the sweep condition their UPDATE on `WHERE status = 'pending_payment'`, so this is a safe no-op by construction — it will never resurrect a cancelled booking back to `confirmed` (which could double-book a room already resold to someone else). This is a known, accepted MVP limitation, not solved further — fully solving it would need refund automation, out of scope.
- No separate "release inventory" step anywhere — `HELD_BOOKING_STATUSES` in `availability.service.ts` already computes availability live from booking `status`, so flipping status off `pending_payment` (to `cancelled` or `failed`) *is* the release, automatically, next time availability is queried.
- `failed` (webhook explicitly told us) and `cancelled` (sweep gave up waiting, no word ever arrived) are kept as distinct terminal states, matching the schema's existing check constraint.

## Problems solved

- Environment note, not a bug: the backend dev server that was already running (pid from an earlier session/terminal) needed a restart to pick up the new route files — restarted cleanly, no issue.
- **Real bug found and fixed after the developer's own browser test** (not caught by my synthetic Stripe-CLI script test, which used a single atomic `create`+`confirm` call and never exercised the race): a pre-existing race condition in Feature 20's `createPaymentIntentForBooking` (`backend/src/services/payment.service.ts`). Root cause: `usePaymentIntent.ts`'s mount effect has no double-fire guard, and React Strict Mode double-invokes effects in Next.js dev — two near-simultaneous `POST /payments/intent` calls both saw `booking.stripePaymentIntentId` as empty (plain check-then-act, no locking) and each created its own Stripe PaymentIntent. The DB stored whichever write landed last; the browser used whichever `client_secret` its own request got back — not guaranteed to be the same one. Confirmed root cause via `stripe.events.list()` on the real account (found two `payment_intent.created` events at the same timestamp per booking, only one of which the browser actually drove to `succeeded`/`payment_failed`). The webhook itself worked correctly — it just couldn't find a booking matching the *actually-confirmed* intent, since the DB pointed at the other, abandoned one.
- **Fix**: wrapped `createPaymentIntentForBooking`'s check-then-act in a `db.transaction` with a new `lockBookingForOwner` query (`SELECT ... FOR UPDATE`, same row-lock pattern `lockRoomTypeForBooking` already used for booking creation in Feature 19). Concurrent calls now serialize and always converge on one PaymentIntent. Verified with a scratch script firing two concurrent calls at the same booking — both returned the identical `client_secret`.
- **Data reconciliation**: 3 real bookings from the developer's own testing were affected by the pre-fix race. Checked each one's true outcome via `stripe.events.list()` (not guessed) and manually corrected in the DB: two that Stripe actually charged successfully were flipped to `confirmed` (with `stripePaymentIntentId` corrected to the intent that was actually charged); one that Stripe actually declined was flipped to `failed` (same id correction). Reasoning: since money had already moved on 2 of these, letting the 20-minute sweep auto-cancel them would have meant keeping the customer's payment while showing a cancelled booking — reconciling to ground truth was the correct call, not auto-cancel.
- **Not yet re-verified**: the fix was confirmed via a concurrent-call scratch script, not yet via a fresh real browser checkout end-to-end. That should be the first thing done next session if the developer hasn't already retried it.
