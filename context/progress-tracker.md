### ✅ 22 Stripe Webhook — completed 2026-07-13
Notes: Backend-only, no UI. New `POST /webhooks/stripe` (`webhooks.routes.ts`, mounted directly in `app.ts` — via `express.raw({ type: "application/json" })` and positioned before `express.json()`, same raw-body-first pattern the app already used for better-auth) → `webhooks.controller.ts` → new `webhook.service.ts`: `constructStripeEvent` verifies the `stripe-signature` header via `stripe.webhooks.constructEvent`, `handleStripeEvent` dispatches `payment_intent.succeeded` → booking `confirmed` and `payment_intent.payment_failed` → booking `failed` (looked up via the `stripePaymentIntentId` column Feature 20 already persists), any other event type is a silent 200 no-op so Stripe doesn't retry-storm us for events we don't care about. Separately, new `POST /bookings/expire-stale` (`bookings.routes.ts`, behind new `requireCronSecret` middleware) runs the abandoned-cart sweep on demand — not a background job, since there's no cron/job-runner dependency or deployment pipeline in the project yet. New `booking.queries.ts` additions: `findBookingByStripePaymentIntentId`, `confirmBookingIfPending`/`failBookingIfPending` (both share a private `transitionBookingIfPending` conditioned on `WHERE status = 'pending_payment'`), and `expireStalePendingBookings(cutoffMinutes)` (single conditional `UPDATE ... WHERE status = 'pending_payment' AND created_at < cutoff`, no separate inventory-release step — `HELD_BOOKING_STATUSES` in `availability.service.ts` already computes availability live off `status`, so flipping status off `pending_payment` *is* the release). New env vars: `CRON_SECRET` (shared-secret header `x-cron-secret`, compared with `crypto.timingSafeEqual`) and `BOOKING_EXPIRY_MINUTES` (default 20).
Decision (confirmed with the developer during `/architect`): the cleanup sweep is an HTTP endpoint the developer (or any external scheduler later) calls, not an in-process `setInterval`/cron dependency — matches the project having no deployment pipeline yet, and doubles as the developer's manual-trigger tool for local testing.
Decision (confirmed with the developer during `/architect`): endpoint protection is a shared-secret header (`CRON_SECRET`) rather than `requireAdmin` — the existing admin/user auth middlewares are both browser-session-based via better-auth cookies, which doesn't work for a machine caller (a real cron service) with no browser session. A shared secret works identically for manual `curl` testing now and a real scheduler later.
Decision (confirmed with the developer during `/architect`): 20-minute expiry window (MVP-appropriate, configurable via `BOOKING_EXPIRY_MINUTES`) — accepted tradeoff: a payment method that settles slowly (e.g. ACH-style "Pay by bank", which Stripe can leave `processing` for hours) could have its late `succeeded` webhook arrive after the sweep already cancelled that booking. Both the webhook handler and the sweep are conditioned on `WHERE status = 'pending_payment'`, so that's a safe no-op by construction — it won't resurrect a cancelled booking back to `confirmed` (which could double-book a room already resold). Left as a known, accepted MVP edge case rather than solved further; solving it fully would need refund automation, which is out of scope.
Problems solved: my own synthetic Stripe-CLI test (script-driven, `paymentIntents.create` + `.confirm` in one call) passed clean, but the developer's very next real browser checkout got stuck on `/booking-confirmation/[bookingId]` with the booking still `pending_payment` despite Stripe showing the charge as `succeeded`. Root cause traced via `stripe.events.list()`: a pre-existing race in Feature 20's `createPaymentIntentForBooking` (`payment.service.ts`) — a plain check-then-act (read `booking.stripePaymentIntentId`, create-and-persist only if empty) with no locking. `usePaymentIntent.ts`'s mount effect has no double-fire guard, and React Strict Mode double-invokes effects in Next.js dev, so two near-simultaneous `/payments/intent` calls both saw `stripePaymentIntentId` as empty and each minted its own Stripe PaymentIntent; the DB ended up storing whichever wrote last, while the browser kept using whichever `client_secret` its own request happened to receive — not guaranteed to be the same intent. The webhook fired correctly for the real (browser-confirmed) intent, but `findBookingByStripePaymentIntentId` found no match since the DB pointed at the *other*, never-confirmed intent — so it correctly no-opped, leaving the booking stuck. Fixed by wrapping `createPaymentIntentForBooking`'s check-then-act in a `db.transaction` with a new `lockBookingForOwner` (`SELECT ... FOR UPDATE`, same row-locking pattern `lockRoomTypeForBooking` already established for booking creation) — concurrent calls now serialize onto one PaymentIntent regardless of how many times the effect fires. Verified with a scratch script firing two concurrent `createPaymentIntentForBooking` calls for the same booking: both now return the identical `client_secret`. The three real bookings affected by the pre-fix race (from the developer's own testing) were reconciled by hand to their true Stripe outcome (checked via `stripe.events.list()`, not guessed): two `succeeded` → manually flipped to `confirmed` with the correct (actually-charged) `stripePaymentIntentId` corrected in the DB; one `payment_intent.payment_failed` → flipped to `failed`, same correction. This bug originated in Feature 20, not Feature 22 — it just had no way to surface until a real webhook existed to check payment outcomes against the DB.
Verified end-to-end: `tsc --noEmit`/`pnpm build` clean for backend after both the webhook implementation and the race-condition fix. Real local pass using the actual Stripe CLI (`stripe listen --forward-to localhost:4000/webhooks/stripe`, real test-mode API, real seeded DB — not mocked): created a real booking + real PaymentIntent, confirmed with `pm_card_visa` → real `payment_intent.succeeded` webhook delivered and verified → booking flipped to `confirmed`. Second booking + PaymentIntent confirmed with `pm_card_chargeDeclined` → real `payment_intent.payment_failed` webhook → booking flipped to `failed`. Unhandled event types delivered during the same run (`charge.succeeded`, `payment_intent.created`, `charge.updated`) all returned a clean 200 without side effects, confirming the no-op path. `/bookings/expire-stale`: missing header → 401, wrong secret → 401, correct secret → 200 with a real backdated (25-minute-old) test booking correctly flipped to `cancelled` — the same real call also swept 13 genuinely stale `pending_payment` bookings that had accumulated in the DB from earlier feature-testing sessions, confirming the sweep works at more than single-row scale. All test bookings created for these tests were deleted afterward; the 13 pre-existing stale bookings were left in their now-correctly-`cancelled` state (that's the feature working as designed, not test residue to clean up). The race-condition fix was confirmed via two concurrent calls against a fresh test booking converging on one `client_secret` — not yet re-verified through a real browser checkout end-to-end; that's the first thing to confirm next session if not already done.

### 09 Search Backend Wiring — 2026-07-07
Decision: Per-date availability/price math (`available_override ?? total_inventory`, `price ?? base_price` over every night of the stay) is computed in plain JS (`availability.service.ts`'s `enumerateStayDates`/`findQualifyingRoomTypes`) over a normal Drizzle `.select()` + `inArray(...)` query, not a SQL `generate_series`/CTE.
Reason: `code-standards.md` requires the query builder over raw SQL strings, and a `generate_series`-based derived table joined with `LEFT JOIN`/aggregated with `bool_and(...)` doesn't fit the chained builder — the alternative (`db.execute(sql\`...\`)` with one large hand-written statement) would be exactly the "raw SQL string" the standard forbids. A stay's date range is always small, so per-date JS aggregation is simpler and just as correct.
Impact: `backend/src/services/availability.service.ts` (new), `backend/src/queries/search.queries.ts`'s `findCandidateRoomTypes`/`findRateOverridesForRoomTypes` (plain builder queries only). ### 09 Search Backend Wiring — 2026-07-07 (bug found during verification)
Decision: Two correlated-subquery filters ("hotel has all requested amenity ids", "room type has all requested room feature ids") were rewritten from `sql\`... = ANY(${idArray}::uuid[])\`` to `sql\`... IN ${idArray}\``.
Reason: Drizzle's `sql` template spreads an interpolated JS array into a parenthesized comma-list (the shape `IN (...)` expects), not a single bound Postgres array value `ANY(...)` needs — the original form threw `malformed array literal` at runtime (single-element array) or produced invalid SQL outright (multi-element). Caught via a real `curl` test against the seeded DB, not by `tsc` (both forms type-check identically). Documented as a general Drizzle gotcha in `library-docs.md`.
Impact: `backend/src/queries/search.queries.ts`. Any future `= ANY(${array})` usage in this codebase should be `IN ${array}` instead.

### 09 Search Backend Wiring — 2026-07-07 (post-`/review` fixes)

(4) `FilterSidebar` and `ActiveFilterChips` each independently fetched the same 3 catalog endpoints (6 requests instead of 3 per page load), and neither handled fetch rejection. Reason: All four were verified against the running app/API before fixing, not assumed from the report alone — (1) and (2) via a real Playwright pass (clicking "View on map" on the *second* hotel card confirmed it selects that specific hotel, not just `hotels[0]`; navigating to `page=2` then switching to Map confirmed hotels still render), (3) via direct `curl` against the seeded DB (`checkOut` in the past now `400`s instead of returning NaN-priced results), (4) via request-count assertion in the same Playwright pass (3 requests, down from 6).

### 02 Database Schema — 2026-07-04
Decision: `backend/src/config/seed.ts`'s `insertLookupTable` helper takes an explicit `LookupRow { name: string; icon?: string }` interface rather than `Record<string, string>`.
Reason: `noUncheckedIndexedAccess` (mandated by `code-standards.md`) makes any property access through an index-signature type like `Record<string, string>` come back as `string | undefined`, even for keys known to exist — `tsc` rejected `row.name` being passed where a `string` was required. Impact: `backend/src/config/seed.ts`. Worth remembering for any future generic "iterate arbitrary key/value rows" code in this codebase — prefer named interfaces over `Record<string, T>` when `strict`/`noUncheckedIndexedAccess` is on and a field is guaranteed to exist.
